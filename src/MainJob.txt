# PROJEKT: RADAR INNOWACJI
## Inteligentny system automatycznego wykrywania potencjalnych innowacji

Jesteś głównym architektem oprogramowania, doświadczonym programistą .NET 10, specjalistą Blazor, AI/ML, przetwarzania danych oraz integracji z zewnętrznymi źródłami informacji.

Twoim zadaniem jest zaprojektowanie i stopniowe stworzenie kompletnej aplikacji o nazwie „Radar Innowacji”.

Projekt realizowany jest w ramach hackathonu i musi posiadać działający prototyp oraz możliwość instalacji na komputerze osoby oceniającej.

Nie twórz całej aplikacji jednocześnie. Pracuj etapami zgodnie z poniższą specyfikacją.

---

# I. CEL PROJEKTU

Radar Innowacji to inteligentna platforma służąca do automatycznego odnajdywania potencjalnie wartościowych innowacji powstających w szkołach, uczelniach, instytucjach publicznych, społecznościach programistycznych oraz innych organizacjach.

System ma wyszukiwać informacje o nowych projektach, prototypach, wynalazkach, pracach naukowych, projektach studenckich i rozwiązaniach technologicznych.

Najważniejszym założeniem jest odnajdywanie projektów, które nie zostały formalnie zgłoszone jako innowacje.

System nie może ograniczać się do wyszukiwania słowa „innowacja”.

Powinien rozpoznawać opisy:
- nowych technologii;
- projektów badawczych;
- prac inżynierskich i magisterskich;
- prototypów urządzeń;
- nowych metod i algorytmów;
- projektów Open Source;
- projektów kół naukowych;
- rozwiązań organizacyjnych;
- rozwiązań społecznych;
- nowych zastosowań istniejących technologii.

Podstawowym celem pierwszej wersji jest skuteczne WYKRYWANIE I GROMADZENIE informacji o potencjalnych innowacjach.

Nie skupiaj się na komercjalizacji, inwestorach ani finansowaniu. Te funkcjonalności mogą zostać dodane w przyszłości.

# II. TECHNOLOGIE

Wykorzystaj następujący stos technologiczny:

### Backend
- ASP.NET Core 10.
- C#.
- Entity Framework Core 10.
- Dependency Injection.
- BackgroundService do cyklicznych zadań.
- HttpClientFactory do komunikacji z zewnętrznymi API.

### Frontend
- Blazor Web App.
- Interactive Server.
- Razor Components.
- Bootstrap 5.
- Responsywny interfejs.
- Język polski.

Nie twórz osobnego frontendu w React ani Angular.

Nie pisz własnego JavaScriptu. Funkcjonalności interfejsu realizuj w Blazor i C#.

Wykresy realizuj za pomocą komponentów Blazor lub SVG generowanego przez Razor.

### Baza danych
- SQLite.
- Entity Framework Core.
- Migracje EF Core.

Baza musi być przechowywana poza katalogiem instalacyjnym aplikacji, w katalogu danych użytkownika.

Architektura ma umożliwiać późniejsze przejście na PostgreSQL.

### AI
- Ollama jako opcjonalny lokalny silnik AI.
- Qwen3 1.7B jako początkowy model językowy.
- Model embeddingowy multilingual-e5-small lub inny odpowiedni model wielojęzyczny.
- Możliwość wyłączenia AI.

AI nie może być wymagane do uruchomienia aplikacji.

System musi działać również bez zainstalowanego Ollama.

### Przetwarzanie danych
- AngleSharp do analizy HTML.
- RSS/Atom do pobierania wiadomości.
- API zewnętrznych serwisów.
- OAI-PMH do pobierania metadanych repozytoriów naukowych.
- Mechanizm pobierania dokumentów PDF, jeżeli pozwala na to źródło.

### Dodatkowe założenia
- Logowanie operacji.
- Obsługa błędów.
- Asynchroniczne pobieranie danych.
- Możliwość anulowania zadań.
- Konfiguracja źródeł bez modyfikowania kodu.
- Brak uzależnienia od zewnętrznej chmury.

Nie dodawaj niepotrzebnych bibliotek. Przed wykorzystaniem dodatkowej zależności sprawdź jej kompatybilność z .NET 10.

# VI. WYKRYWANIE POTENCJALNYCH INNOWACJI

System musi wykorzystywać kilka mechanizmów.

### Etap 1 – filtr regułowy

Wstępnie analizuj tytuły, opisy i metadane.

Szukaj sformułowań:
- opracowano;
- zaprojektowano;
- skonstruowano;
- stworzono prototyp;
- nowa metoda;
- nowa technologia;
- autorski system;
- innowacyjne rozwiązanie;
- badania nad;
- autonomiczny system;
- inteligentny system.

Nie odrzucaj automatycznie materiałów, które nie zawierają tych słów.

### Etap 2 – analiza AI

Wykorzystaj Ollama.

Domyślny model: Qwen3 1.7B Q4.

AI powinno analizować materiał i zwracać ustrukturyzowane dane.

Przykładowy wynik:

{
  "isPotentialInnovation": true,
  "confidence": 85,
  "innovationType": "Technologiczna",
  "problem": "Problem rozwiązywany przez projekt",
  "solution": "Opis proponowanego rozwiązania",
  "noveltyDescription": "Co może być nowe",
  "technologies": ["IoT", "AI"],
  "reason": "Uzasadnienie",
  "suggestedCategories": ["Robotyka", "AI"]
}

To przykład schematu, nie sztywny zestaw kategorii.

AI nie może przedstawiać przypuszczeń jako potwierdzonych faktów.

Jeżeli brakuje informacji, ma to wyraźnie zaznaczyć.

### Etap 3 – status odkrycia

Wprowadź trzy statusy:

1. Candidate – znaleziony materiał potencjalnie interesujący.
2. Interesting – AI wskazuje, że warto go dokładniej zbadać.
3. Verified – człowiek potwierdził jego wartość.

Status Verified wymaga ręcznego zatwierdzenia.

### Etap 4 – praca bez AI

Jeżeli Ollama nie działa:
- system nadal pobiera materiały;
- stosuje filtry regułowe;
- zapisuje wyniki;
- oznacza materiały jako wymagające analizy AI;
- pozwala na późniejsze przetworzenie.

# VIII. ŚWIEŻOŚĆ I ZAKRES DAT

Jest to jedna z najważniejszych funkcji projektu.

System ma rozróżniać:

1. PublishedAt – data publikacji materiału.
2. EarliestKnownDate – najwcześniejsza znana data powstania projektu.
3. LastActivityAt – ostatnia znana aktywność projektu.
4. DiscoveredAt – moment odnalezienia materiału przez Radar.

Nie zakładaj, że data publikacji jest datą powstania innowacji.

Jeżeli nie można ustalić daty, zapisuj NULL.

Nie wymyślaj dat.

Wprowadź filtry:

- ostatnie 7 dni;
- ostatnie 30 dni;
- ostatnie 90 dni;
- ostatnie 6 miesięcy;
- ostatni rok;
- ostatnie 2 lata;
- wszystkie;
- własny zakres dat.

Umożliw osobne filtrowanie według:
- daty publikacji;
- daty powstania projektu;
- daty ostatniej aktywności;
- daty odkrycia przez Radar.

Stwórz wskaźnik FreshnessScore.

Świeżość powinna być oddzielona od oceny wartości innowacji.

Nie usuwaj starszych projektów z bazy tylko dlatego, że użytkownik wybiera krótki zakres dat.

Historia ma być zachowywana.

# XIV. INSTALATOR I URUCHAMIANIE

To wymaganie krytyczne.

Projekt jest przeznaczony do demonstracji na komputerze osoby oceniającej.

Nie może wymagać:
- Visual Studio;
- JetBrains Rider;
- zainstalowanego SDK .NET;
- PostgreSQL;
- zewnętrznego serwera.

Przygotuj aplikację jako samodzielny program dla Windows x64.

Wykorzystaj:
- self-contained deployment;
- ASP.NET Core Kestrel;
- lokalną bazę SQLite;
- Inno Setup do stworzenia instalatora EXE.

Oczekiwany sposób działania:

1. Tester uruchamia plik instalacyjny.
2. Instalator instaluje aplikację.
3. Tworzony jest skrót na pulpicie.
4. Tester uruchamia Radar Innowacji.
5. Program uruchamia lokalny serwer.
6. Automatycznie otwiera przeglądarkę.
7. Wyświetla się dashboard.

Aplikacja powinna działać lokalnie pod adresem localhost.

Zabezpiecz uruchomienie:
- nasłuchuj wyłącznie na loopback;
- nie wystawiaj aplikacji do sieci lokalnej bez wyraźnej konfiguracji;
- obsłuż konflikt portu;
- zapobiegaj uruchamianiu kilku niepotrzebnych instancji;
- umożliwiaj poprawne zamknięcie aplikacji.

Dane użytkownika przechowuj poza katalogiem instalacyjnym.

Instalator nie powinien zawierać Ollama ani dużych modeli AI.

Jeżeli AI nie jest dostępne, aplikacja ma nadal działać.

- instrukcję uruchomienia;
- instrukcję odinstalowania;
- możliwość zachowania lub usunięcia danych przy deinstalacji.

RadarInnowacji-Setup.exe
